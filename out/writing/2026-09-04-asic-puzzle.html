Solving the Jane Street ASIC reverse-engineering puzzle

Jane Street recently published a puzzle on reverse engineering an ASIC. Given a layout file:

We need to figure out a) what this ASIC does, and b) try to coax a value out of it that doesn't read like gibberish.

Let's start with what we're given! First off, if we download the repo, we can see that we're given the GDS file for this as shown above (which we can view with KLayout or the TinyTapeout GDS viewer as mentioned in the puzzle description); an image of the layout that is supposed to "hint at its functionality"; and an example waveform so we can see the relationship between the inputs and outputs.

From the layout image, I got kind of hopeful because you can see that all the inputs we can toggle are single-bit. While we don't know that the functionality of each of these inputs necessarily match up to the respective label, let's just assume they're true, and take a gander at what this chip might do!

  • Whatever we are doing, there's some sort of sequential logic going on, since there's a clock! A sequential circuit can be represented by a finite state machine.

  • We only have one bit of serious input, input, which indicates we are serially communicating something.

  • Therefore, we can derive this as some of state machine where we have to input the right set of input bits — input=0,1[], to set success to high. You can call this whatever you want, e.g. it's a password checker or whatever.

Other than this info, there isn't much more use we're going to get out of this picture, I think. But now our guess is that if this is a state machine, we can figure out how to get it to a more useful representation, namely:

f(S,I)=S′

where S is the set of all state and I is the set of changing inputs. This is actually overly verbose because I is technically part of S, but I find this to be clarifying.

Once we're there we can figure out how to brute force it, or maybe we'll be able to notice patterns on our own.

Next up is the waveform (to open it, the puzzle mentioned Surfer, which is what I used to inspect the puzzle):

I'm not an expert at this so right now I'm not really deriving any useful info from this; maybe this could come in handy later though, since in a puzzle there is a purpose to everything! There are three Easter eggs (or ish) in the waveform file though — .vcd files are just text:

  • The date is funny, "Sat Dec 31 23:59:60 2016". At first I thought it was just peculiar because "2016", but apparently this is a leap date.

  • Version: "Leave no stone unturned! But for this file, consider looking at it in a waveform viewer instead."

  • The output, which at each step/cycle is one byte, produces the ASCII sequence "TRY AGAIN" twice.

Extracting the netlist

If we open the GDS file in KLayout or TinyTapeout — I used the latter for this part — we can see that the cell instances have their types intact:

This is really really good, because the SkyWater PDK is open source and we can use it to derive a netlist from the GDS file. I wasn't really sure how to do this so I asked a LLM. It turns out there there's this thing called LVS, which is short for Layout Vs. Schematic.

Essentially, it's a script you write to confirm that the layout matches a given schematic — a SPICE netlist. Specifically, it converts a layout back to SPICE, then tries to make sure it's functionally equivalent to a SPICE netlist you pass in. This means that we can remove the latter step — we don't have a SPICE netlist on hand — and just use the script to derive the SPICE netlist.

KLayout's documentation has a wonderful introduction to LVS here that has an example of a LVS script. I won't go into too much more in detail here.

Writing this LVS script by hand is tedious, so it's either write/prompt a program to do it, or find a program that already exists. Fortunately, Efabless has a LVS script that we can install inside KLayout by going to Tools > Manage Packages > searching "Efabless_sky130 1.0.7" and installing it.

We can pull that script into our puzzle directory and then remove the parts that do the comparison. Alternatively, you can also find it here in their repo.

Verifying what we've got

At this point in time, I thought it was a good time to verify that the two steps we've taken so far, GDS → SPICE → Verilog, actually produce output that we might expect. To do this, we would have to compare our generated Verilog netlist to a golden Verilog netlist.

Of course, we don't have one of those. And this is where the warmup puzzle comes in handy, because it does have a golden Verilog netlist, warmup/01_netlist.v!

We can do this comparison with a tool like Yosys1(1) I only knew about this because I was messing around with Yosys to do the exact opposite of what this puzzle is about. See the notes at the end of this post.: Yosys is "an open source framework for RTL synthesis". RTL stands for Register Transfer Level. Basically Yosys lets you do manipulations on HDLs that describe hardware as a list of instructions that manipulate and move data between registers, eventually synthesizing such an abstraction down to actual flip flops and logic circuits. Such HDLs are said to operate at the Register Transfer Level.

In this case, Verilog is such an HDL, so Yosys can parse it into an IR and then manipulate it. Along the way, it can simplify the IR and then compare it to another simplified IR.

To do this in Yosys, we simply send in a list of commands and a lot of IR manipulation magic happens on the backend. We can also send in a script like so: 

read_verilog 01_netlist.v
read_verilog produced_netlist.v

# Process into Yosys' internal representation.
proc
# Simplify memory. 
memory
# Flatten so cells are directly nested.
flatten
# Optimize, this is made of the smaller Yosys optimize commands.
opt

check -assert -mapped
equiv_make adder_demo produced equiv
equiv_simple equiv
equiv_status -assert

Feel free to refer to the Yosys command reference for more details.

I got two errors while trying to run this. The bigger error is that both netlists make use of SkyWater cells, and Yosys has no idea what these functionally look like; in other words, we haven't mapped them yet.

By default, Yosys is fine with treating these as a black box and ignoring them; check -assert -mapped asserts that that doesn't happen.

So we have to import them. Fortunately, the PDK has the functional Verilog for each cell that we need. The other issue I ran into was that the Verilog netlist we generated has power ports/rails that the golden netlist doesn't have. We don't need those anyway, since we're curious about the logic of our chip. Let's just do some preprocessing:

preprocess() {
  # Strip power/body tie-off pins (not ports on the official models), normalize
  # drive-strength suffixes (dfrtp_2 -> dfrtp), and remove the empty connection
  # slots left behind by the stripped pins (e.g. "(, .A(x), ... ,)" -> "( .A(x), ...)").
  perl -pe '
    s/\s*\.(VPWR|VGND|VPB|VNB|sky130_gnd)\s*\([^)]*\)//g;
    s/sky130_fd_sc_hd__([a-z0-9]+)_[0-9]+/sky130_fd_sc_hd__$1/g;
    # Remove the empty connection slots left by stripped pins and any runs of
    # adjacent commas (looping until stable).
    1 while s/\(\s*,+/(/g;   # leading empty slot: "(, , .a(..)" -> "("
    1 while s/,\s*\)/)/g;    # trailing empty slot: ".a(..), ... ,)" -> ")"
    1 while s/,\s*,+/,/g;    # inner runs: "...,, ..." -> "... ,"
  ' "$1"
}
preprocess 01_netlist.v > "$WORKDIR/pp_01.v"
preprocess produced_netlist.v > "$WORKDIR/pp_net.v"

Solvers come to the rescue

This seems like we could try to pass this into a constraint solver, which I'd heard of vaguely before. My main worry would be the number of iterations this would take — in theory we could go on ad infinitum!, but the hope is that the many constraints here limit the choices we have and thus reduce the search space.

I asked a LLM what the best general-purpose solver I could get up and running with was and it gave me Microsoft's Z3.

Z3, from what I can understand, is a collection of solvers that can perform SMT. To understand SMT, you have to understand SAT, which is short for satisfiability. SAT allows you to solve for boolean equations like:

(¬a∨b)∧(a∨¬b∨c)∧(¬c)

How do we get this to produce true as an answer? By relying on the fact that boolean equations are commutative, we can group parts into AND statements (as denoted by the parentheses), OR statements, and individual unary statements (NOT, or a variable by itself) to simplify the equation. From there, we can determine constraints (i.e., c above must be false for ¬c to evaluate to true), and then mess around with setting variables to true/false until we either reach SATisfied or UNSATisfied (impossible to satisfy, either literally or within time/memory constraints). The last part is the bread and butter of SAT solvers.

SMT, which is short for Satisfiability Modulo Theories, builds on top of this by figuring how to apply different kinds of solvers (different kinds of theories?) to solve problems that are similar to SAT problems, but for more general atoms. In our case, numbers:

x+2y−z=7

3x−y+2z=13

2x+y+z=10

To understand how to use Z3, I found A Dumb Introduction to z3 to be useful. Even though it makes use of the Rust bindings, it's not too different from the Python bindings; for example, the above systems of equations solved with Z3:

import z3

x, y, z = z3.Reals('x y z')

s = z3.Solver()
s.add(x + 2 * y - z == 7)
s.add(3 * x - y + 2 * z == 13)
s.add(2 * x + y + z == 10)

print(s.check())
# sat
print(s.model())
# [x = 5, z = -2/3, y = 2/3]

Now that we have a sequence, we can simulate this until success is flipped low again. In this case, we can simply take advantage of our transition function to simulate this, really cleanly in fact:

import dataclasses
import logic

I_BITS = "00000001010100001000000000000101010100000000000010100000010000010000001000001010000100000001000000100000100100010100000000"
TAIL_BITS = "0" * 64


def fmt(o):
    if 32 <= o <= 126:
        return f"0x{o:02x} ({chr(o)})"
    return f"0x{o:02x} (none)"


bits = [int(c) for c in I_BITS] + [int(c) for c in TAIL_BITS]
st = logic.initial_state()
chars = []
seen_ascii = False

print(f"feeding up to {len(bits)} bits (prefix {len(I_BITS)} + tail), enable=1, rst_n=1\n")

step = 0
for bit in bits:
    step += 1
    st = logic.next_state(
        dataclasses.replace(st, I=bit, enable=1, rst_n=1),
        debug_signals=False,
    )
    _, sig = logic.next_state(st, debug_signals=True)
    o = sig["O"]
    ascii_ok = 32 <= o <= 126

    if seen_ascii and not ascii_ok:
        print(f"step {step:3d}: I={bit}  O={fmt(o)}  ASCII=' '  success={getattr(st, 'success')}  <- stopped: no longer ASCII")
        break
    if ascii_ok:
        seen_ascii = True

    ch = chr(o) if ascii_ok else ""
    chars.append(ch)
    ascii_ch = ch if ch else " "
    print(f"step {step:3d}: I={bit}  O={fmt(o)}  ASCII='{ascii_ch}'  success={getattr(st, 'success')}")

msg = "".join(chars)
print("\nfull message displayed:", repr(msg))

  • Having never done this before, I took a couple of extra steps that I probably didn't need to take. I tried to detail that in this post, at the expense of maybe being a bit confusing :)

  • I didn't talk much about the three parsers that were used to solve this puzzle because I didn't write them, but as you can imagine they're really primitive, just lexer → parser produces an AST/IR → traverse through AST and produce final format.
