What is a linker

A linker is just a program that combines various pieces of code and data into one file that can then be loaded and executed. Different OSes support different formats. ld on Linux is used to invoke the linker, for example, and it's just a binary.

I think it's helpful to take a look at what happens exactly when you run a compiler driver. Usually, it follows a set of steps:

  1. Some sort of preprocessor runs on your code. As an analogy, I like to think of this as a find + replace operation with constants (e.g., files, macros, etc.) if you will. In C, this is what header files are

  2. Some sort of compiler runs on your preprocessed code, compiling down into an intermediate representation (IR). Compilers also tend to do extra things to facilitate a easier time for the next couple of steps, e.g. optimizations, mangling the names of functions, etc etc.

  3. Some sort of assembler runs on your compiled code, compiling that IR down to your instruction set architecture (ISA) of choice. This typically depends on your host system - i.e., typically represented

  4. Some sort of linker runs on your assembled code, combining it with other assembled code to form an execuable. The file a linker produces, the executable, can usually be executed in the right conditions (i.e. supported architecture, etc.)

You can semantically combine the first three and refer to them as a translator. In addition, these steps are typically run by a compiler driver, e.g. GNU or Clang, which are programs that simply abstract away all these steps with the options you pass in.

Linkers are a useful, necessary step in modern systems because besides producing working executables, it's an extra optimization step3(3) Many such cases.. For example, many modern systems have the concept of shared libraries - i.e., shared code. For example, using when you use printf

I think a good way to understand this a little bit more and to motivate writing a linker is to look at this process through the lens of trying to build and then run an actual program. Let's take a look at a "Hello, world!" program of sorts.

First, an example program

Here's an example main.c:

#include <stdio.h>

int sum(int *a, int n);

static int count = 42;
static int array[3] = {1, 2, 5};

int main() {
  printf("Hello, world!\n");
  count += sum(array, 3);
  return count;
}

As you can see, we define a function called sum that hasn't actually been defined yet. This is because we've defined it in sum.c:

static int count = 4;

int sum(int *a, int n) {
  int i, s = 0;

  for (i = 0; i < n; i++) {
    s += a[i];
  }

  return s + count;
}

On memory

I'm going to take a quick detour to discuss memory in modern systems. If you know about this stuff you can just skip this

Early CPUs started out with segmentation. The 80868086(8086) Random, but I like to remember, which was a 16-bit microprocessor, introduced segmentation to increase the amount of addressable memory from 16 bits to 20 bits - i.e., from 64KiB to 1MiB.

Segmentation introduces the notion of segments; a segment is a virtual view into physical memory; how far is this virtual address from the actual address, i.e., an offset? They're just values stored in a segment register: CS for code segment; SS for stack segment;

In the initial version of segmentation, segment registers directly contained the offset. Protected mode was introduced later on (in x86, enabled by toggling bit in control register CR0) that introduces the notion of a local/global descriptor table (LDT/GDT), with the segment register containing an index into one of these tables. The tables themselves contains a descriptor for the segment - the size, permissions, etc. The descriptor

Segmentation introduced the notion of virtual memory: applying transformations on a virtual address to a physical address. That way, we can have multiple processes running on theoretically fixed addresses - which is

The problem with segmentation is that it introduces fragmentation: we need to be constantly moving things around in memory for things to fit. As a result, segmentation isn't really utilized nowadays, except for backward compatibility reasons. (For example: booting conventions still tend to make use of segmentation to make the jump from 16-bit compatibility mode, termed real mode, to protected mode, and then finally to long mode.)

Nowadays paging is used. Paging keeps the notion of virtual addresses, but introduces the concept of pages rather than segments. Pages are just fixed blocks of memory; 4KiB is the typical page/frame size on x86-64. Then, instead of having the local/global descriptor table, we have

The nice thing about this is that virtual addresses on x86-64 directly map to page table entries (PTE). Each table index is 9 bits (29=512 entries), and the final offset is 12 bits. The remaining two bytes (64−(9∗4=36+12=48)=16) are currently empty.

Zig 0.16 introduces breaking changes, notably the new I/O pattern where I/O becomes a more defined interface that can be passed around similar to the Allocator interface.
